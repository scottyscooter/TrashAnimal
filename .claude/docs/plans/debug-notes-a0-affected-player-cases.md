## Notes on cases explicitly checked and ruled out

- `CardStashedEvent`, `TokenResolutionStartedEvent`, `DieRolledEvent`, `CardDrawnPrivatelyEvent`, `PlayerBustedEvent` — all self-only; `ActingPlayerSeat` is always the sole affected party (the event is either private to them or public-but-symmetric, no other single seat is targeted).
- `CardPlayedEvent` — currently only emitted for Nanners/Blammo/MmmPie bust-recovery/repeat plays via `RollPhaseLogEventFactory.ForBustRecoveryCardPlayed` ([RollPhaseLogEventFactory.cs:26-27](TrashAnimal/GameLog/RollPhaseLogEventFactory.cs#L26-L27)), which always passes `TargetSeat: null`. The type supports a target, but nothing in the codebase currently sets one — no live gap today, but if a future targeted card play reuses this event, its `TargetSeat == viewerIndex` branch in `BuildCardPlayedMessage` ([GameLogProjector.cs:117-125](TrashAnimal/GameLog/GameLogProjector.cs#L117-L125)) is already viewer-correct and ready to be toasted once A1 lands.
- Bandit's per-opponent `CardStashedEvent` (a responder stashing a match, [TokenPhaseBanditHandler.cs:92](TrashAnimal/TokenPhase/Services/TokenPhaseBanditHandler.cs#L92)) is self-caused by the responder's own dispatched action (`TokenBanditMatchPass`'s sibling, the stash-pick command) — they already get their own `onSuccess` feedback; not a "someone else acted on me" case.
- TokenPhase Shiny/Feesh interrupts ([TokenPhaseInterruptCardPlay.cs](TrashAnimal/TokenPhase/Services/TokenPhaseInterruptCardPlay.cs)) route through the same `StealAttemptedEvent`/`ForShinyStealBegun` path as RollPhase Shiny — already covered by row 3, no separate row needed.
- StashTrash/DoubleStash/DoubleTrash/Recycle token resolution — all self-only (the active player draws/stashes their own cards); no other seat's state changes.

## Note on `AffectedPlayerSeats`: single seat vs. list

Every case in this table that has a genuinely *targeted* non-actor party (rows 1-8) has **exactly one** affected seat — including Kitteh-swap (row 2). The plan doc's stated rationale for defaulting to a list — "Kitteh-swap affects two players" — conflates two different things: Kitteh-swap changes *two* players' roles, but the player who dispatched the action (the original victim, now the new thief) already gets their own feedback for free via `dispatch()`'s existing `onSuccess` handling. The *only* party this feature needs to reach that isn't already covered is the other one — the new victim — which is a single seat (`NewVictimSeat`). The same pattern holds for every other row: `ThiefSeat`, `TargetSeat`, `VictimSeat`, the Yum Yum roller, the current Bandit/Yum-Yum responder, and the new `CurrentPlayerIndex` are all singular.

The one case that's structurally a broadcast rather than a targeted seat is row 9 (game end) — but that's better modeled as "always toast this event type to every viewer" than as an `AffectedPlayerSeats` list, since literally everyone but the actor qualifies and a list would just be "all other seats" spelled out.

**Recommendation: override the plan doc's default. Make `AffectedPlayerSeat` a single nullable `int?`, not a list.** No discovered case requires more than one targeted seat, and a nullable scalar is simpler for both the projector to populate and the frontend hook to filter on than an `IReadOnlyList<int>?` that will only ever contain zero or one element in practice. If a genuinely multi-seat-targeted event is added later, revisit then rather than paying the list's complexity cost now for a case that doesn't exist in the current catalog.
