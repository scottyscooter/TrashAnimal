# Fix: Steal token never exhausts, and gets stuck when no opponent has cards

## Context

Testing surfaced two related bugs in TokenPhase's Steal-token resolution:

1. **Steal token never exhausts.** After a player resolves a Steal token, it remains offered as an allowed action indefinitely — the player can steal repeatedly instead of the token being consumed once.
2. **Game gets stuck when no opponent has any cards.** If every opponent's hand is empty when the player picks the Steal token, there's no way to progress: the command fails with an error every time, and nothing ever consumes the token or advances the turn.

Root cause (confirmed by reading the code, `main` @ `f35daed`): `TrashAnimal.Api` never calls the token-exhaustion machinery for Steal at all. `TrashAnimal/GameSession.ApiSupport.cs:164-203` (`TryStartTokenStealWithVictimChoice` — the method `GameApplicationService.ExecuteTokenStealUnlockedAsync` actually calls) reimplements the candidate check and calls `_steal.Begin(...)` directly, but never touches `TokenPhaseState.RemainingTokens`/`ActiveToken`. The correct pattern lives in `TrashAnimal/TokenPhase/Services/TokenPhaseTokenResolver.cs:49-57` (`TryStartToken`'s Steal branch, used only by the CLI's delegate-driven path) — it removes the token from `RemainingTokens` and sets `ActiveToken` before the steal starts, so that when `GameSession.StealYumRoll.cs` finishes the steal, `TokenPhaseCoordinator.OnStealResolvedWhileInTokenPhase` (`TokenPhase/TokenPhaseCoordinator.cs:146-153`) sees `ActiveTokenIsSteal == true` and calls `FinishCurrentTokenPassOrRepeat`. Since the API path never sets `ActiveToken`, that check is always false, so the token is never removed and the turn can never auto-complete if Steal is the last token.

Bug #2 (stuck with zero targets) exists in **both** paths: `StartHandSteal` (`TokenPhaseTokenResolver.cs:286-320`) and the API's inline duplicate (`GameSession.ApiSupport.cs:179-184`) both return `false` + an error string when `Opponents.GetAllWithNonEmptyHand` is empty, leaving `RemainingTokens` untouched — so the same unresolvable token is offered again next query, forever. Nothing today auto-resolves a token that has zero valid targets, and there's no domain event or response channel for "resolved but had no effect" (confirmed via `TrashAnimal/GameLog/GameLogEvent.cs` and `GameCommandResult`/`GameCommandResponse` — success responses carry no message field, only `View`/`AllowedActions`).

**Bandit has an analogous-but-distinct edge case, confirmed by reading `TrashAnimal/TokenPhase/Services/TokenPhaseBanditHandler.cs`.** Bandit itself does not have the "zero valid targets" bug — it never requires a target to start; every opponent is simply queued to respond (stash-or-pass), and the queue always drains and calls `FinishCurrentTokenPassOrRepeat` regardless of how anyone responds. But `StartBandit` (lines 111-135) can fail for a different reason: if the draw pile is empty (`DealCards(1)` returns 0 cards), it returns `false` with `error = "Deck is empty."` — and the caller, `TokenPhaseTokenResolver.TryStartToken`'s Bandit branch (`TokenPhaseTokenResolver.cs:76-84`), reacts by re-adding Bandit to `RemainingTokens` and returning `false`, leaving the token perpetually available and perpetually failing the same way. This is the same *shape* of stuck-forever bug as Steal's zero-candidates case, just triggered by deck exhaustion instead of opponent hand state. Not encountered in manual playtesting (rare — needs the deck to run out exactly when Bandit is picked), but confirmed reachable by reading the code, so it's included in this fix.

No existing test catches any of these: `TrashAnimal.Api.Tests/Integration/TokenPhaseCommandKindsTests.cs`'s `ResolveTokenSteal_FullFlow_ThiefReceivesCardFromVictimHand` (lines 146-182) exercises the exact buggy method but never asserts on `RemainingTokens`/`AllowedActions` afterward (unlike the sibling Recycle test in the same file, which does), and no test sets up a zero-opponent-cards or empty-deck-during-Bandit scenario at all.

## Backend fix (TrashAnimal domain)

**Goal:** one code path owns "start/resolve the Steal token," used by both the API and the CLI, so exhaustion is never duplicated/forgotten again; any token that can't produce its normal effect (Steal with no hand candidates, Bandit with an empty deck) auto-resolves and exhausts instead of erroring forever; and none of this leaks state that corrupts a later token's resolution.

1. **New domain event, generalized (not Steal-specific)** — `TrashAnimal/GameLog/GameLogEvent.cs`: add `TokenResolvedWithNoEffectEvent(SequenceNumber, TurnNumber, ActingPlayerSeat, TokenAction Token)` — "this token was picked but its normal effect couldn't happen, so it resolved with no effect." One event shape, reused for both Steal (no hand candidates) and Bandit (empty deck), since the fact is the same shape in both cases ("token X resolved without producing its effect") — only the human-readable *reason* differs, and that's a projection concern, not a new fact type. Add the projection case in `TrashAnimal/GameLog/GameLogProjector.cs`, branching the wording on `Token` (e.g. Steal → `"{actor} picked a Steal token, but no opponent had a card — nothing happened."`; Bandit → `"{actor} picked a Bandit token, but the deck was empty — nothing happened."`).

2. **Centralize zero-effect handling in `TokenPhaseTokenResolver`** (`TrashAnimal/TokenPhase/Services/TokenPhaseTokenResolver.cs`), applied consistently to **both** entry points a token can start from — `TryStartToken` (first pick) and `RestartSubflow` (MmmPie repeat, lines 342-376) — since a repeat attempt can hit the same zero-effect condition the first attempt did:
   - **Steal**: in both `TryStartToken`'s Steal branch (lines 49-57) and `RestartSubflow`'s Steal case (line 365-366), check `Opponents.GetAllWithNonEmptyHand` for candidates *before* calling `StartHandSteal`. If empty: remove the token from `state.RemainingTokens` (only relevant for `TryStartToken` — already removed by the time a repeat runs), ensure `state.ActiveToken` stays/becomes `null`, record `TokenResolvedWithNoEffectEvent(Token: Steal)`, and route through `FinishCurrentTokenPassOrRepeat(state, out error)`.
   - **Bandit**: in both `TryStartToken`'s Bandit branch (lines 76-84) and `RestartSubflow`'s Bandit case (line 362-363), if `_bandit.StartBandit(state, out error)` fails (deck empty — its only failure mode), do the same thing instead of today's "re-add token, return false": remove from `RemainingTokens`/clear `ActiveToken`, record `TokenResolvedWithNoEffectEvent(Token: Bandit)`, route through `FinishCurrentTokenPassOrRepeat`.
   - **Critical fix to `FinishCurrentTokenPassOrRepeat` itself** (lines 322-340): today it only clears `state.ResolveTokenTwice` inside the `if (state.ResolveTokenTwice && state.ActiveToken is { } activeForRepeat)` branch (line 325-327). A token that fizzles via the new zero-effect path never sets `ActiveToken`, so that condition is false and `ResolveTokenTwice` is never reset — meaning if a player played MmmPie and then picked a token that fizzled, the "resolve twice" flag would silently survive and incorrectly double-resolve whatever token they pick *next*. Fix: `ResolveTokenTwice` must be unconditionally cleared whenever a token finishes (fizzled or not), not only on the actual-repeat branch. (The MmmPie card itself is still correctly spent regardless — `TokenPhaseInterruptCardPlay.TryPlayMmmPie` discards it immediately on play, independent of what happens to the token chosen afterward; no refund/reversal is needed or wanted — a player who "wastes" MmmPie on what turns out to be a dead token bears that as a normal gameplay outcome. Only the internal `ResolveTokenTwice` bookkeeping leak needs fixing, not the card cost.)
   - **`TryStartToken`'s and `RestartSubflow`'s own signatures do not change** — both keep their existing `out string? error` only. The zero-effect fizzle is handled *inside* their Steal/Bandit branches (removing the token, recording the event, calling `FinishCurrentTokenPassOrRepeat`) and still returns `true`/`null error` for that call — the CLI's delegate-driven path never needs to distinguish "resolved normally" from "resolved with no effect" beyond what the `GameLog` event already records for display. Only the API-facing surface described below needs an explicit `resolvedWithNoEffect` signal, because that's what becomes the HTTP response's `InfoMessage` — don't thread a new out-parameter through `TryStartToken`/`RestartSubflow` itself, since that would force every existing caller (`TokenPhaseGameActionDispatcher`, the MmmPie repeat path) to handle a flag they have no use for.
   - Add two new public methods on `TokenPhaseTokenResolver`, exposed through `TokenPhaseCoordinator` with matching signatures (`TokenPhaseCoordinator` delegates 1:1, same pattern as its other `Try*` methods):
     - `bool TryResolveStealAutoWithNoTargets(TokenPhaseState state, out string? error)` — asserts there really are zero candidates (defensive re-check, never trust the caller), then does the fizzle sequence (remove from `RemainingTokens`, clear `ActiveToken`, record `TokenResolvedWithNoEffectEvent(Token: Steal)`, call `FinishCurrentTokenPassOrRepeat`). Returns `true` unless the defensive re-check fails (candidates actually exist — a race/misuse case).
     - `bool TryStartHandStealWithVictim(int victimIndex, TokenPhaseState state, out string? error)` — the *victim already chosen* path: validates the victim is in the non-empty-hand candidate set, calls `_session.Steal.Begin(...)`, then performs the same `RemainingTokens.Remove`/`ActiveToken = TokenAction.Steal` mutation `TryStartToken` does. This becomes the single implementation the API path also uses (replacing its inline duplicate in `GameSession.ApiSupport.cs`).
   - Bandit's fix stays entirely internal to `TokenPhaseTokenResolver`/`TokenPhaseBanditHandler` — no new coordinator-level method needed, since Bandit was never bypassed by a separate API method the way Steal was; the existing `TryStartToken`/`RestartSubflow` Bandit branches just get the corrected failure-handling in place.
   - Remove the now-redundant zero-candidate check inside `StartHandSteal` (`TokenPhaseTokenResolver.cs:295-300`) once the caller checks first, rather than leaving duplicate dead logic that could drift out of sync again (the same class of mistake that caused bug #1).
   - Note for whoever implements this: the existing lock-and-log lines at the top of `TryStartToken` (`state.TokenResolutionStartLocked = true` and `RecordTokenResolutionStarted(token)`, lines 44-47) already run *before* the `if (token == TokenAction.Steal)`/Bandit branches — no need to move or duplicate them for the new fizzle paths, they already fire unconditionally for every token including one that's about to fizzle.

3. **Fix `GameSession.ApiSupport.TryStartTokenStealWithVictimChoice`** (`TrashAnimal/GameSession.ApiSupport.cs:164-203`): new signature `bool TryStartTokenStealWithVictimChoice(int playerIndex, int? victimIndex, out string? error, out bool resolvedWithNoValidTargets)`. Logic:
   - Validate phase/turn as today (same error strings — don't invent new wording for cases that already have an established message).
   - Ask `_tokenPhaseCoordinator` for the current non-empty-hand candidates.
   - If none: reject a non-null `victimIndex` (defensive — client should never send one, same "No opponent has a card in hand to steal." error as today if it does), otherwise delegate to the new coordinator zero-target method, set `resolvedWithNoValidTargets = true`, return `true`.
   - If some exist: require a non-null `victimIndex` in the candidate set (reuse the existing "Selected victim does not have cards in hand..." error text if it's null or invalid), then delegate to the new coordinator "begin with victim" method (which now does the exhaustion bookkeeping) instead of touching `_steal`/`State`/`RemainingTokens` inline. `resolvedWithNoValidTargets = false` on this branch.
   - This removes the duplicated candidate-check/`_steal.Begin` code from `ApiSupport` entirely — it becomes a thin adapter over `TokenPhaseCoordinator`, matching how `TryPlayShinyWithVictimChoice`/`TryPlayFeeshWithCardChoice` already delegate.

Add a defaulted `string? infoMessage = null` parameter to `BuildResultAsync` itself (so the other 7 call sites need no changes) and pass it into `GameCommandResult.Ok(view, allowedActions, infoMessage)` on the success branch.

## UX addition: general-purpose on-demand info affordance (first applied to the Shiny card)

While reviewing why Steal can't just "hide itself" like Shiny does, a related gap surfaced: when Shiny genuinely can't be played (no opponent has anything in their stash), the game gives **zero feedback** — confirmed by reading `GameBoardPage.tsx:168-178`, where the "Play Shiny" button is wrapped in `allowedActions.includes('PlayShiny') &&`, so it simply doesn't render at all when ineligible. A player holding a Shiny card in `PlayerHand` sees no action anywhere and has to guess why.

The fix for that is one instance of a genuinely general-purpose primitive, not a disabled-state-specific widget: **there is nothing in `InfoBadge`'s behavior — the hover/focus/click/pin mechanics, the positioning, the accessibility wiring — that has any idea what the text it displays means.** It's "attach an on-demand info bubble to any element," full stop. "Why can't I play this" is simply the first content someone chooses to put in it. The same component works identically for explaining what a token does before it's picked, clarifying a count on screen, or any other passive contextual detail that doesn't deserve a permanent on-screen label. Naming and framing below are chosen to keep that generality obvious rather than accidentally coupling the component to ineligibility messages:

- **New component**: `src/components/InfoBadge.tsx` (top-level `components/`, not nested under `gameboard/`, specifically so any future page/feature can reuse it — matches how `Toast` already lives at the top level rather than inside a feature folder). Props: `info: string | null | undefined`, `children: ReactNode`.
  - When `info` is falsy, it renders `children` unwrapped with no extra markup at all — no badge, no wrapper `div` — so callers can pass a possibly-null value unconditionally without branching at the call site, and an element with nothing to explain looks and behaves exactly as it does today.
  - When `info` is set, it wraps `children` in a small `position: relative` container and adds a small circular `<button>` badge (an "i" glyph) anchored to the top-right corner of whatever it wraps, styled with the existing `gb-glass` utility classes used elsewhere (e.g. `VictimPicker.tsx`) so it looks native to the board rather than a generic browser tooltip.
  - **Three ways to reveal it, one way to keep it open**: mouse hover and keyboard focus (`Tab` to the badge) both reveal the bubble transiently — it closes again on mouse-leave/blur, the behavior sighted-mouse and keyboard users already expect from tooltips. A click/tap instead "pins" the bubble open regardless of hover/focus state, so a touch-only user (who can't hover at all) still has a reliable way to read it — dismissed by tapping the badge again, clicking elsewhere, or `Escape`. This three-mode behavior is deliberate, not incidental — hover-only tooltips are unusable for touch and for keyboard-only navigation, and this codebase already takes keyboard/touch parity seriously elsewhere (`PlayerHand.tsx`'s Feesh card uses `role="button"`/`tabIndex`/`onKeyDown` for the same reason) — the badge is a real `<button>` with an `aria-label`, not a `div` relying on a CSS `:hover` trick, specifically so it's Tab-reachable and screen-reader-announceable.
  - **Positioning is fixed and simple**: always top-right of the wrapped element, bubble always opens upward (`bottom: 100%` of the badge). No collision-detection/auto-flip logic — deliberately skipped since the codebase has no positioning library today (e.g. Floating UI) and the board's layout is predictable enough (cards live near the bottom of the screen, so "open upward" almost always has room) that the added complexity isn't justified yet. If a future placement needs smarter positioning, that's a reason to add a real positioning dependency then, not to over-build this primitive now.
- **First application, Shiny**: `PlayerHand`'s current props are `{ handCards, allowedActions, onFeeshClick }` (`PlayerHand.tsx:5-9`) — no turn-state prop exists today. Add exactly one new prop: `shinyDisabledExplanation: string | null`. Compute it once in `GameBoardPage.tsx` — **already gated on turn state at the computation site**, so `PlayerHand` itself never needs an `isLocalPlayerTurn` prop:
  ```
  const shinyDisabledExplanation =
    isLocalPlayerTurn && !allowedActions.includes('PlayShiny') && gameView.opponents.every(o => o.stashFaceDownCount === 0 && o.stashFaceUpCards.length === 0)
      ? 'No opponent has anything in their stash to steal.'
      : null
  ```
  Pass it down: `<PlayerHand ... shinyDisabledExplanation={shinyDisabledExplanation} />`. Inside `PlayerHand`'s per-card map (lines 26-72, currently only Feesh gets a `title` attribute and click handling), wrap **only the card where `card.name === 'Shiny'`** in `<InfoBadge info={shinyDisabledExplanation}>` — every other card in the fan is untouched by this change.
- **Known limitation, stated explicitly**: this specific Shiny message is a best-effort, client-derived explanation covering the single most common ineligibility cause (no valid stash targets) — the same category of client-side approximation already used for the Steal victim-picker fix above. It does not mirror every server-side eligibility rule (e.g. a just-drawn/`NewlyAdded` Shiny card being temporarily ineligible mid-TokenPhase-pass per `TokenPhaseCardEligibility.CanPlayCardForActionDuringTokenPhase`) — in that narrower case the badge simply won't appear (falls back to no explanation, same as today), rather than showing a wrong reason. A fully accurate reason for every case would require the backend to expose a structured ineligibility reason per hand card on `GameView`/`HandCardView`, which is a larger contract change out of scope for this pass. This limitation is specific to the Shiny use case, not to `InfoBadge` itself — any future caller supplying accurate `info` text (e.g. static rules text, or a value already correct by construction) doesn't inherit it.
- **Reusability**: this is the whole point of building `InfoBadge` as a standalone primitive instead of a Shiny-specific fix — the same component can later attach to any hand card, token, or button on the board for any purpose (MmmPie's "can't play right now", a disabled DoubleStash submit button, a token's rules text on hover, an opponent's stash count breakdown, etc.) by computing an `info` string wherever that screen has something worth explaining, with no new plumbing and no change to `InfoBadge` itself.
- **Visual treatment, for whoever styles this**: reuse existing tokens rather than introducing new ones — `VictimPicker.tsx`'s `gb-glass`/`gb-glass-hover` utility classes for the badge/bubble surface, and `var(--gb-text-primary)`/`var(--gb-text-label)` for text (same pairing used throughout `gameboard/`). The disabled Shiny card itself should be visually dimmed (e.g. reduced opacity, matching the mockup shown during planning) in addition to the badge appearing — the badge alone, on an otherwise full-strength card, doesn't read as "this is currently unavailable" at a glance; the dimming is what signals that, and the badge is what explains why. One layout note: `PlayerHand`'s fan already wraps each card in a transformed, animated container (hover scale/lift, `zIndex: isHovered ? 100 : index`, `PlayerHand.tsx:41-64`) — `InfoBadge`'s wrapper `div` should sit *inside* that existing per-card container (not as a sibling positioned independently), so the badge moves and scales naturally with the card during the fan's hover animation instead of needing its own separate positioning logic.
